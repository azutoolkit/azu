# Database dashboard (CQL integration)

The dev dashboard's **Database** tab shows every SQL statement an Azu app runs: KPIs, N+1 analysis,
recent queries tagged with the request that ran them, slow queries, query patterns, transactions,
connection pool usage and a read-only SQL playground.

The tab is fed through CQL's event framework only: `Azu::CQL::Instrumentor` subscribes to `CQL::Telemetry`
(one query event per statement, one transaction event per begin/commit/rollback) and records them in
`Azu::QueryStore`. Azu does not wrap or patch CQL, and anything that emits those events shows up. It needs a CQL
release newer than 0.0.533 (`CQL::Telemetry.subscribe_transactions` and `CQL::Schema#pool_stats`); older releases fail
to compile with a message saying so. Telemetry reports affected rows for writes only, so SELECT row counts show "-",
and parameter values only appear when you turn on `CQL::Telemetry.capture_params` (otherwise `?` placeholders). Without `azu/cql` the tab falls back to CQL's own performance monitor (when `cql`
is required before `azu`), or shows an "n/a" card that explains how to install the event bridge. Once `azu/cql` is
installed, the statements recorded in `Azu::QueryStore` take precedence.

Azu core does not depend on CQL. The integration is opt-in and lives in one initializer of your app,
which configures CQL with its own `configure` and attaches the dashboard:

```crystal
# src/initializers/cql_config.cr
require "pg"           # or sqlite3; add `cql` and the driver to your shard.yml
require "azu/cql"

Azu::CQL.configure do |c|            # forwards to CQL.configure
  c.db = ENV["DATABASE_URL"]
  c.pool.size = 10
end

Azu::CQL.attach { AppDB }            # the dashboard resolves AppDB the first time it needs it
```

```crystal
# src/db/schema.cr
AppDB = Azu::CQL.schema :app do      # URL, adapter and pool come from CQL.config
  table :users do
    primary :id, Int64
    column :name, String
  end
end
```

That is the whole setup. Models, queries, transactions and migrations are plain CQL
(`include ::CQL::ActiveRecord::Model(Int64)`, `db_context schema: AppDB, table: :users`), and every
query shows up in the dashboard tagged with the request that ran it. A runnable PostgreSQL example laid out
like this is [`playground/azu_cql_postgres`](https://github.com/azutoolkit/azu/tree/master/playground/azu_cql_postgres).

* **Why `attach { }`?** Initializers load before `db/schema.cr`, and a schema file regenerated by CQL's dump is a plain
  `CQL::Schema.define`. The block is only evaluated when the dashboard needs the schema, so it works with either form.
  A one-file app can define the schema in the initializer instead: `AppDB = Azu::CQL.schema :app { ... }` (it attaches itself).
  An existing schema can be attached directly: `Azu::CQL.attach(AppDB)`.
* **Which URL?** In order: the `uri` argument of `Azu::CQL.schema`, `CQL.config.db` once it has been set, then
  `Azu::CONFIG.database.uri` (deprecated; defaults to `DATABASE_URL`). With none of them `Azu::CQL.schema` raises.
  The adapter comes from the scheme (`postgres://`, `postgresql://`, `mysql://`, `sqlite3://`; anything else raises).
* **Pool settings.** When the URL comes from `CQL.config`, `c.pool.size`, `c.pool.max_idle_size` and `c.pool.checkout_timeout`
  are appended to it as crystal-db parameters (`max_pool_size`, ...). Parameters already in the URL always win.
  Azu does not use `CQL.config.full_db_url`, which drops the URL's own query string and injects SSL and auth settings:
  put `?sslmode=require` in the URL yourself.
* **Lazy connection.** The schema is created without opening a socket (`initial_pool_size=0`), so the app, console and tasks boot
  without a database and the first query connects. Turn it off with `Azu.configure { |c| c.database.lazy_connect = false }`
  (`AZU_DB_LAZY=false`), per schema with `Azu::CQL.schema(:app, lazy: false)`, or with `initial_pool_size` in the URL.
  To fail fast (for example at boot in production) call `Azu::CQL.verify!(AppDB)`.
* **While the database is down** the Database tab still renders: the pool card shows no open connections and the SQL playground
  reports the connection error.

CQL's types are also reachable under the Azu namespace (`Azu::CQL::Schema`,
`Azu::CQL::ActiveRecord::Model`, ...), so an app that does `include Azu` never has to name `::CQL`, and
`CQL.configure` inside such a namespace is `Azu::CQL.configure`.

## CQL on PostgreSQL: things to know

* Build records with `User.new(...)` and `save!`. `User.create!(...)` reads the new id back with `last_insert_id`, which
  PostgreSQL does not provide in current CQL (the insert succeeds, then the lookup of id 0 fails).
* Use `Model(Int64)` with `primary :id, Int64`, and `class` for models.
* Declare real indexes with `schema.alter(:users) { create_index :users_email, [:email], unique: true }`. `index:` inside
  `schema.table` emits no SQL.
* `CQL::Migrator` writes the database URI into `src/schemas/app_schema.cr` while `auto_sync` is on; pass
  `MigratorConfig.new(auto_sync: false)`. Its tracking table is `cql_schema_migrations`.
* Pass association foreign keys explicitly: `has_many :posts, Post, foreign_key: :user_id`.
  `dependent:` is never applied (use `on_delete: :cascade` on the foreign key) and `preload` works for `has_many` only.
* `CRYSTAL_ENV` must be set before CQL's configuration is first created: its environment defaults (pool sizes, SSL) are applied
  at that moment, not when `c.env` is assigned.

## Moving parts

| Piece | Where | Role |
| --- | --- | --- |
| `CQL::Telemetry` | cql `src/telemetry.cr` | query and transaction events; zero cost without subscribers |
| `Azu::CQL::Instrumentor` | `src/azu/cql/instrumentor.cr` | subscribes (as `azu.dashboard`) and records the events in `Azu::QueryStore` |
| `Azu::RequestContext` | `src/azu/request_context.cr` | fiber-keyed current request (id, endpoint, method, path); set by `Handler::RequestId` and `Endpoint#call` |
| `Azu::QueryStore` | `src/azu/query_store.cr` | bounded store (2000 queries), N+1 analysis, transactions, pool snapshot |
| `Dashboard::DatabaseData` | `src/azu/components/dev_dashboard/database_data.cr` | numbers for the tab: from `QueryStore` when an integration is installed, else from CQL's monitor |
| `Dashboard::DatabaseSection` | `src/azu/components/dev_dashboard/database_section.cr` | server-rendered cards (queries, transactions, pool, playground) |
| `dashboard.js` | `src/azu/components/dev_dashboard/dashboard.js` | the playground's `fetch`; the tab itself refreshes with the dashboard's soft refresh |
| `Handler::DevDashboard` | `src/azu/handler/dev_dashboard.cr` | serves `POST {path}/sql` for the playground |

Other ORMs can feed the same dashboard by calling `Azu::QueryStore.instance.record_query` and setting an `Azu::DatabaseAdapter`.

## Configuration

```crystal
Azu.configure do |c|
  c.database.uri = "sqlite3://./app.db"  # deprecated: use CQL.configure { |c| c.db = ... }; fallback of Azu::CQL.schema (default ENV["DATABASE_URL"])
  c.database.lazy_connect = true         # AZU_DB_LAZY: connect on the first query
  c.database.instrument = true           # AZU_DB_INSTRUMENT
  c.database.n_plus_one_threshold = 3    # AZU_DB_N_PLUS_ONE_THRESHOLD
  c.database.slow_query_ms = 50.0        # AZU_DB_SLOW_QUERY_MS (flagged in the tab and logged as a warning; 0 disables the log)
  c.database.playground = true           # AZU_DB_PLAYGROUND
end
```

## N+1 detection

Within one request, a `SELECT` whose normalized shape (literals and bindings replaced by `?`, `IN` lists collapsed)
runs at least `n_plus_one_threshold` times is reported with its count, total time, call site and an eager-load hint.

## SQL playground

The card appears only when the environment is `Development`, a database is attached and `database.playground` is on; the endpoint additionally requires a loopback client.
Requests must be same-origin POSTs with `X-Requested-With: azu-dashboard`. One `SELECT` / `WITH` / `EXPLAIN` statement is accepted
(no comments, no writes), runs in a transaction that is always rolled back, and returns at most 200 rows.

## Naming gotcha

`include Azu` makes `Azu::CQL` visible as `CQL` inside your namespace, and CQL's own macros expand `CQL::ActiveRecord::...` there.
`azu/cql` therefore mirrors every `::CQL` type into `Azu::CQL`, so models keep working. Inside your own code, prefer `::CQL::...` when you mean the ORM.
