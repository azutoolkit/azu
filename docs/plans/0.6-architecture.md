# Azu 0.6: apps as values

Status: **proposal, for review.** No code in this PR. Phase 2 of the plan to make Azu the best Crystal web
framework; the two Phase 2 pieces already merged are the `Azu::Routable` endpoint interface (#66) and the
CI that keeps the suite honest (#54, #59, #62).

## The problem in one paragraph

Azu has one global application. `Azu::CONFIG` is a constant, `Configuration#router` is its only router,
and the endpoint macros (`get "/users"` inside a struct body) register on that router while the class body
runs. Requiring `azu` already starts work. Measured on Crystal 1.22 with a program that is only `require "azu"`:
it sets the root log level to `Debug` and replaces the log backend, creates the upload temp directory, and has
seven named fibers running (`upload-cleanup`, four `log-batch-worker-N`, `log-flush-timer`, `error-reporter`).
Several handlers also read `CONFIG` directly. The costs:

- **No second app.** Mounting an admin app under `/admin`, or running two apps in one process, is impossible.
  `Router::Builder#@scope` is stored and never used, so `routes :web, "/test"` does not prefix anything.
- **Tests share state.** `Azu.with_config` swaps configuration per fiber, but the router, the template
  registry and the cache are still global, so specs cannot run in parallel and leak into each other.
- **Surprises at `require`.** A library that requires `azu` gets a log backend, a directory and a fiber.
- **Contracts are optional.** A `Request` struct is validated only if the endpoint remembers to call it; the
  default handler stack is empty, so a new app has no request id, no error pages and no security headers
  unless the author adds them.

Size of the change: about 50 `CONFIG` references and 19 `current_config` uses in `src/`, 14 spec files that
mention `CONFIG`, and the playground. It is a refactor of a known surface, not a rewrite.

## Principles

1. **An app is a value.** `Azu::App.new` owns its `Configuration`, `Router`, handler chain, template
   registry and cache. Nothing global is needed to run one.
2. **The old way keeps working for one minor.** `Azu::CONFIG`, `Azu.configure`, `include Azu` and the endpoint
   macros stay as a deprecated shim over a default app, with a deprecation log line, and are removed in 1.0.
3. **Each slice ships alone.** Every slice below is a PR that keeps the suite green on Crystal 1.19.1 and
   latest, so there is never a long-lived branch.
4. **Failing spec first.** Each slice starts with a spec that fails today.
5. **Stdlib first.** `HTTP::Server#close`, `Process.on_terminate`, `WaitGroup`, `Log`, `HTTP::Cookies`,
   `MIME::MediaType` before any hand-rolled code.

## Target shape

```crystal
# An app is built, not declared at require time.
app = Azu::App.new(env: :production) do |config|
  config.port = 8080
end

app.routes do
  get "/users/:id", UserEndpoint          # explicit, on this app
  scope "/api" do                          # a scope that really prefixes
    post "/users", CreateUserEndpoint
  end
  mount Admin::App.new, at: "/admin"      # another app, prefixed
end

app.start                                  # default handler stack, then listen, then drain on TERM/INT
```

The existing style keeps working:

```crystal
module MyApp
  include Azu
  configure { |c| c.port = 4000 }          # configures Azu::App.default
end

struct UserEndpoint
  include Azu::Endpoint(UserRequest, UserResponse)
  get "/users/:id"                         # registers on Azu::App.default
end

MyApp.start [Azu::Handler::RequestId.new] of HTTP::Handler
```

Both styles can mix: macros register on the default app, explicit `app.routes` on any app.

## Slices, in order

Each slice lists what changes, the spec that fails first, and the compatibility story.

### 1. No work at `require` (small, no API change)
- Move `Log.setup` out of `Configuration` into `App#start` (and `Azu.setup_logging` for libraries that want it).
- Make `UploadConfiguration` lazy: create the directory and start the cleanup fiber on first upload or in `start`.
- Same for the async log workers, flush timer and error reporter (`log_format.cr`): start them with the app.
- Spec: a program that only requires `azu` has no `upload-cleanup`, `log-*` or `error-reporter` fiber
  (`Fiber.each`), creates no directory and leaves the root `Log` level and backend alone.
- Compat: log output in an app that never calls `start` changes (no azu formatter); documented in the guide.

### 2. `Azu::App` over the existing pieces
- New `Azu::App` holding `Configuration`, `Router`, a `HandlerPipeline`, and the template registry.
  `Azu::CONFIG` becomes `Azu::App.default.config`; `Azu.current_config` keeps its fiber-local override.
- Handlers and endpoints stop reading the `CONFIG` constant and ask the app they run in (carried by
  `RequestContext`, which already tags the current request per fiber).
- Spec: two `App` instances with different routes and config, driven in one process, answer independently.
- Compat: `configure`, `CONFIG`, `Azu.start`, `include Azu` unchanged in behaviour; they emit one deprecation log.

### 3. Routes belong to an app; scopes and mounts work
- `App#routes { }` with `get/post/.../ws/scope/mount`. `scope` actually prefixes (fixing the unused
  `Builder#@scope`). `mount other_app, at: "/admin"` strips the prefix for the child and gives its URL helpers
  the prefix at runtime.
- Endpoint macros register on `App.default` unless the endpoint is registered explicitly.
- URL helpers (`UserEndpoint.path(id: 1)`) resolve the prefix from the current request's app, so the same
  endpoint mounted twice links correctly.
- Spec: an endpoint mounted at `/a` and `/b` answers on both and links to itself with the right prefix.

### 4. Contracts are enforced
- The request struct is validated before `call`; a failure becomes a typed `422` with field errors as
  RFC 7807 `application/problem+json`. The parsed request is memoised per call (today a second access
  re-parses).
- Malformed JSON or form bodies are `400`, not `500`; body size is enforced before buffering.
- Spec: an endpoint never calls validation and still never sees an invalid request.
- Compat: the error body shape changes; the old shape stays available behind `config.error_format = :legacy`
  for one minor.

### 5. A default handler stack
- `App#start` without handlers builds `RequestId, Logger, Rescuer, SecurityHeaders, Static`.
- New handlers: `SecurityHeaders` (HSTS, CSP, X-Frame-Options, Referrer-Policy), `Compression` (on
  `HTTP::CompressHandler`), `HealthCheck`.
- Passing an explicit handler array keeps today's behaviour exactly (nothing is added behind the author's back).

### 6. Lifecycle
- SIGTERM and SIGINT stop accepting, wait for in-flight requests (a `WaitGroup`) up to
  `config.shutdown_timeout`, then close. Fixes the `e == Errno` check in the restart loop, which never matches.
- `App#start`/`#stop` are callable from specs, so tests boot an app on `bind_unused_port` instead of a
  prebuilt binary.

### 7. Optional subsystems out of core
- The dev dashboard (about 4,400 lines) and the performance monitor move behind `require "azu/dev"` and one
  compile-time macro instead of ~25 repeated `{% if env("PERFORMANCE_MONITORING") %}` blocks.
- Spec: `require "azu"` alone does not load the dashboard (extends the existing opt-in boundary spec).

## What this deliberately does not change
- The typed contract (`Endpoint(Request, Response)`) and `Response#render`.
- Spark, PubSub and channels, except that they read config from the app.
- `Azu::Routable`, `HTTP::Handler` chains and everything Rack-like users already know.

## Risks
| Risk | Mitigation |
|---|---|
| Hidden readers of `CONFIG` | grep-gate spec: no `CONFIG` constant in `src/` outside the compat shim |
| Macro registration order differs when an app is explicit | registration is idempotent per (app, method, path); duplicate still raises `DuplicateRoute` |
| Compile-time cost of more generics | each slice compiles the whole suite on 1.19.1 and latest in CI |
| `authority` depends on `azu ~> 0.5.31` | shims keep it compiling; update it in lockstep after slice 3 |
| Crystal compiler bugs (a union of two modules miscompiled struct endpoints in #66) | prefer module includes to unions; reproduce in a tiny program before designing around it |

## Decisions for the maintainer
1. **Is `Azu::App.default` + a deprecation shim the right compatibility story**, or should 0.6 break
   `Azu::CONFIG` outright? (Recommended: shim for 0.6, remove in 1.0, as in the plan.)
2. **Explicit `app.routes` as the new primary style, macros as sugar?** Or keep macros primary and make
   `mount` a macro too? (Recommended: explicit routes primary, macros kept.)
3. **Error format**: adopt RFC 7807 `problem+json` as the only format in 0.6, or keep the legacy shape behind
   a flag for one minor? (Recommended: flag for one minor.)
4. **Order**: slices 1 to 3 first (they unblock mountable apps and parallel tests); 4 to 6 can follow in
   any order. OK?

## Migration guide outline (written alongside slice 2)
- What a deprecation line looks like and how to silence it while migrating.
- `include Azu` + `configure` to `Azu::App.new`.
- Endpoints are `Azu::Routable`, not `HTTP::Handler` (#66).
- Error body format.
- Testing with `Azu::App` and `bind_unused_port`.
